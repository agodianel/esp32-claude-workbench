# AGENTS.md — ESP32 firmware project

> Instructions for AI coding agents (Claude Code, Codex, Cursor, Copilot, Gemini CLI,
> Antigravity) working in this ESP-IDF project. Generated by `esp32wb init`.

## Core principles

1. **Never edit code without an implementation contract.** Every change starts with a
   contract: scope, risks, tests, rollback. Small changes get a short contract, not none.
2. **Test before claiming done.** Every deliverable includes test evidence.
3. **Respect hardware constraints.** Memory, timing and peripherals are real limits.
4. **Preserve mission state.** Update the active file in `missions/` after each step.
5. **Never guess hardware facts.** Pin rules differ between ESP32, S2, S3, C2, C3, C5, C6,
   H2 and P4. Look them up with the tools below; cite the source.

## Tools — use them instead of guessing

Prefer the `esp32-workbench` MCP tools when connected; otherwise use the CLI
(`esp32wb`, or `uvx --from git+https://github.com/agodianel/esp32-claude-workbench esp32wb`).

| Need | MCP tool | CLI |
|------|----------|-----|
| Pin facts for the target chip | `chip_info` | `esp32wb chip <target>` |
| Before/after any GPIO change | `pin_audit` | `esp32wb pins .` |
| Full project health check | `project_doctor` | `esp32wb doctor .` |
| Before peripheral / ADC / Wi-Fi / BLE code | `search_esp_docs` | `esp32wb docs search "<q>"` |
| Release readiness | `sdkconfig_review`, `partition_check` | `esp32wb sdkconfig sdkconfig`, `esp32wb partitions partitions.csv` |
| Crash / panic | `crash_decode` | `esp32wb crash log.txt --elf build/<app>.elf` |
| Build or flash failure | `build_log_triage` | `idf.py build 2>&1 \| esp32wb build-log -` |
| Serial log | `log_summary` | `esp32wb logs log.txt` |

The target is read from `CONFIG_IDF_TARGET` in `sdkconfig` / `sdkconfig.defaults`.

## Hardware rules (all targets)

- Never use pins wired to SPI flash or in-package PSRAM. Which pins those are depends on
  the chip and module — run `esp32wb chip <target>`.
- Treat strapping pins as boot-critical: external pull-ups/downs or loads on them can stop
  the chip from booting or change flash voltage.
- Avoid the UART0 console pins and the USB-Serial-JTAG D-/D+ pins unless you intend to give
  up the console / USB flashing.
- Input-only pins exist only on some chips (classic ESP32: GPIO 34–39, no pulls).
- ADC2 and Wi-Fi: on classic ESP32, ADC2 cannot be used while Wi-Fi is active; on S2/S3
  reads are arbitrated and can fail. Prefer ADC1 for anything sampled with Wi-Fi on.
- Document every GPIO assignment in one `pin_map.h` (or a pin map at the top of `main.c`).
- Check peripheral allocation for conflicts before adding a driver. Configure every pin
  explicitly; never rely on board defaults.

## Memory

- Heap is shared with Wi-Fi/BLE/LWIP. Monitor `esp_get_free_heap_size()` and
  `esp_get_minimum_free_heap_size()`.
- Buffers > 512 bytes go on the heap, not the stack. Check every allocation for NULL.
- DMA buffers: `heap_caps_malloc(size, MALLOC_CAP_DMA)`. Never allocate in an ISR.
- Watch for fragmentation in long-running devices.

## FreeRTOS

- Always give explicit stack sizes: ≥ 2048 bytes for simple tasks, ≥ 4096 for Wi-Fi/BLE/TLS.
- Yield with `taskYIELD()`, never `vTaskDelay(0)`.
- ISRs only call `*FromISR` APIs; defer work to a task.
- Protect shared state with mutexes (priority inheritance), not by disabling interrupts.
- Feed the task watchdog in long operations (`esp_task_wdt_reset()`).

## Error handling

- Check every `esp_err_t`. `ESP_ERROR_CHECK()` only for fatal init errors.
- At runtime: log, retry with exponential backoff (network), or degrade gracefully.
- Log with the right level: `ESP_LOGE/W/I/D/V`. Never log secrets.

## Workflow

1. Create or open a mission: `esp32wb mission new "<feature>" -d "<goal>" --target <chip>`.
2. Write the implementation contract (`esp32wb contract ...`) and get it accepted.
3. Write the test plan; implement within the contract scope.
4. Run tests and `esp32wb doctor .`; record results in the mission.
5. Prepare the PR with rationale, test evidence, risk notes and rollback.

## Coding standards (C)

- ESP-IDF style; `snake_case` functions/variables, `UPPER_SNAKE_CASE` macros.
- Component prefixes (`wifi_manager_init()`), `static` for file-scope functions.
- Include guards `#ifndef COMPONENT_NAME_H`; Doxygen comments on public APIs.

## Every change reports

1. What was tested, 2. how (commands), 3. results with output, 4. what was **not** tested and why.
