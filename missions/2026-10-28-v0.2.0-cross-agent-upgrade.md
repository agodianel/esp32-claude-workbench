# Mission: v0.2.0 — Cross-agent, multi-chip workbench

## Goal

Turn the workbench from a Claude-Code-only, classic-ESP32-only repo into an installable,
multi-chip toolkit whose skills work in Claude Code, OpenAI Codex, Cursor, GitHub Copilot,
Gemini CLI and Google Antigravity, backed by one tested Python package (CLI + MCP server).

## Board / Target

- **Chip**: ESP32, ESP32-S2, ESP32-S3, ESP32-C2, ESP32-C3, ESP32-C5, ESP32-C6, ESP32-H2, ESP32-P4
- **Board**: DevKit V1 and M5Stack profiles (data-driven, extensible)
- **ESP-IDF version**: v5.x

## Constraints

- Breaking changes accepted for v0.2.0 (approved 2026-10-28): kebab-case skill names,
  `mcp/` folder replaced by the `esp32_workbench` package, Python ≥ 3.10.
- Core package must stay standard-library only so skill scripts run anywhere with `python3`.
- Heavy ML dependencies (torch, faiss) must be optional (`[semantic]` extra).
- Every chip fact must cite an Espressif primary source. Unknown → `null`, never guessed.
- Skills must pass the agentskills.io spec (name charset, name == folder, description ≤ 1024).

## Design Notes

- **One core, many front-ends.** `esp32_workbench` holds all logic. The `esp32wb` CLI (with `--json`),
  the MCP server, the Claude hooks and the skills all call it. This removes the duplicated, inconsistent
  rules that lived in `mcp/tools/` vs `tools/` (e.g. GPIO 5 strapping in one, not the other).
- **Chip database as data.** `data/chips/<target>.json`; target auto-detected from `CONFIG_IDF_TARGET`.
- **Skills are self-describing and tool-backed.** Each skill tells the agent to run `esp32wb …` and
  falls back to `uvx --from git+…` when not installed. Playbooks become per-skill `references/`.
- **Docs search.** Default: SQLite FTS5 (stdlib). Optional: existing FAISS semantic index.
- **Missions are written to the user's project** (cwd / given root), not the workbench clone.

## Implementation Contract

### Non-goals
- Publishing to PyPI or the plugin marketplaces (prepared, not executed).
- On-target (hardware-in-the-loop) test execution.
- ESP8266 or Arduino-core-specific rules.

### Risk Assessment
- **Data correctness: HIGH.** A wrong pin rule gives false confidence. Mitigation: primary-source
  research with citations stored in each chip file, tests pin known facts per chip.
- **Migration: MED.** Existing MCP configs break. Mitigation: CHANGELOG migration section.
- **Concurrency / peripheral / memory: N/A.** Host-side tooling only, no firmware changes.

### Test Plan
- [ ] Existing 148 tests ported and passing.
- [ ] Per-chip pin rule tests (classic ESP32 behaviour unchanged; S3/C3/C6 rules correct).
- [ ] Crash decoder: Xtensa and RISC-V panic fixtures; addr2line invoked only when present.
- [ ] Partition checker, build-log triage, FTS docs search, mission round-trip (create → validate).
- [ ] Every `skills/*/SKILL.md` validated against the Agent Skills spec in pytest.
- [ ] Installer writes to the correct per-agent paths (tmp dirs).
- [ ] `ruff check` + `ruff format --check` on the whole repo.

### Rollback Strategy
All work is on branch `upgrade/v0.2.0`. `main` is untouched. Rollback = delete the branch.
